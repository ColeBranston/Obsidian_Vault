
**1. Partitions**

- Spark divides data into partitions: each partition is processed by one task.
- Number of partitions defaults to:
	- for `local[*]`, roughly `nums_cores` partitions (for `parallelize()`).
	- For file-based reads, default is `spark.sql.files.maxParitionBytes` / HDFS block size, or `spark.default.parallelism`.
- You can explicitly set partitions with `repartition(n)` (full shuffle) or `coalesce(n)` (narrow dependency).

2. **Narrow vs Wide Transformations**

    - **Narrow transformations** (e.g., `map`, `filter`, `withColumn`) do not require data across partitions and can be pipelined.
    - **Wide transformations** (e.g., `groupBy`, `join`, `distinct`, `orderBy`) require data to be shuffled across executors. These trigger a shuffle, which is expensive (network I/O, serialization, disk spill).

3. **Shuffles**

    - During a shuffle, data is moved between executors. Spark writes intermediate files to disk, network transfer happens, then data is read back.
    - **Minimize shuffles**:
        - Predicate pushdown (`filter` early).
        - Project only needed columns (`select(…)`).
        - Use broadcast joins when one DataFrame is small.
        - Use `mapPartitions` or map-side aggregations where possible.

4. **Tuning**
    - **spark.sql.shuffle.partitions**: default is 200; if your data is small, reduce to avoid creating too many small tasks.
    - Adjust executor memory (`spark.executor.memory`) and cores (`spark.executor.cores`) to balance parallelism vs memory headroom.
    - **Broadcast join**: `spark.conf.set("spark.sql.autoBroadcastJoinThreshold", <bytes>)` or explicitly use `broadcast(small_df)` from `pyspark.sql.functions.
